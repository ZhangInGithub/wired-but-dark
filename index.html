The POC-to-production gap

Wired but Dark

Everyone ships stateful agents now. Statefulness is a property of the read path — not the store. Two harnesses passed every demo and were quietly stateless in production.

Retrospective · self-built harness audit Aug 2026 Read time ~8 min

The most expensive bugs in an agent stack aren't the ones that crash. They're the ones that return a plausible value — an empty list, a well-formed string — and let everything downstream keep running as if the system worked. The harness passes its demo, ships, and only reveals the hole under real traffic, months later, as "the agent feels like it has no memory" or "tools work, except when they don't."

I audited a production harness built to orchestrate a 14B-parameter open model across a fleet of specialist sub-agents. On paper it had everything: persistent context, a tool layer, a supervisor router. Two of those pillars were hollow — not missing, hollow. The scaffolding around them was complete enough that no one noticed. Here are both, generalized to the pattern, because if you've built a harness around a small model you have probably shipped at least one of them.

TRAP 01

The wired stub memory that saves perfectly and reads back nothing

The harness had a real persistence layer. Context was written to a store on every turn — with append semantics, version-conflict retries, identity checks, a dual-write mirror. A get_context_service was injected into twelve call sites across the sub-agents. By every structural measure, memory was wired.

Then the read path: get_context_messages(). The body that transformed stored records back into model messages had been commented out during some past refactor and replaced with a bare return []. Its one caller — the master turn loop — dutifully fetched history at the top of every request and received an empty list. The README promised "resume any conversation by its contextId." The code wrote that history faithfully and never read a word of it back.

Why it hides so well: every observable signal is green. The store fills. Save calls succeed. Twelve injection points resolve. Dashboards show context written. The single severed hop is a pure-function transform with no side effect to monitor — and the model, handed an empty history, simply behaves like a stateless chatbot, which reads as "small models are just forgetful," not "our read path returns a literal empty list."

2026 lens The ecosystem now sells this pillar by name — "universal memory layer," "stateful agents," "durable execution." But a memory layer that writes and never reads is a write-only log, and statefulness is a property of the read path. This isn't a missing feature; it's a durability failure wearing a green dashboard.

The tell

Infrastructure breadth is not infrastructure depth. Twelve call sites wired to a service says the plumbing is done; it says nothing about whether water comes out. Grep your persistence and tool layers for return [], return None, pass, and TODO sitting inside functions the README describes as working.

TRAP 02

The text-JSON detour tool calls parsed out of prose with a regex

Modern model endpoints expose native function calling: the model emits a structured tool_calls field, the runtime reads name and arguments straight off it, dispatch is unambiguous. The harness I audited didn't use it. Instead it prompted the model to print a fenced JSON block, then recovered the call with re.search(r'```json ... ```') over the raw text — and bound tools natively only in a mock path that production never touched.

This works in the demo because a 14B model, well-prompted, usually formats the block correctly. "Usually" is the whole problem. The moment the model wraps the JSON in a sentence, emits two blocks, trails a comma, or the regex meets a nested brace, the parse silently misses — and a missed parse is indistinguishable, downstream, from "the model chose not to call a tool."

2026 lens By now this isn't even a build-vs-buy call. The ecosystem standardized tool calls into a protocol — MCP, spec revision 2025-11-25, adopted across the major frameworks — precisely so nobody hand-rolls the model↔tool boundary anymore. Parsing JSON out of prose isn't a shortcut past that; it's opting out of the one contract everyone else converged on.

There's a second, subtler reason to prefer the native field even though it, too, can break: when it breaks, it tends to break loudly. Which brings up its sibling —

Sibling failure · same boundary

Native tool calling isn't automatically safe either. On OpenAI-compatible endpoints served by some inference backends, streamed tool_calls continuation chunks repeat name and id as an explicit null where the reference API simply omits them. An accumulator written as if (delta.name !== undefined) lets that null overwrite the real name captured in the first chunk — and every call arrives as unknown tool "". The fix is != null. This is the failure class a protocol exists to kill — and it survives anyway, because the standard specifies the shape, not the wire drift of every backend claiming to speak it. Same lesson as Trap 02, one layer down: even on the native path, the boundary between you and the model is where provider conventions diverge, and where "usually fine" parsing goes to die.

Why 2026 makes this sharper

Statefulness is a property of the read path.

The agent conversation has moved on. The pitch is no longer "can it call a tool" — it's stateful agents, durable execution, a universal memory layer. Which is exactly why these two traps matter more, not less: they're the gap between the property a harness advertises and the one it actually has. All three failures are invisible in the demo and visible only in the trajectory.

  • Trap 01 is a durability failure. A store that writes and never reads is a write-only log. If your system is sold as stateful, an amnesiac read path isn't a missing feature — it's the headline promise, broken silently.
  • Trap 02 is opting out of the standard. The ecosystem converged on a protocol for the model↔tool boundary (MCP, rev 2025-11-25) so nobody hand-rolls it. Parsing tool calls out of prose in 2026 is choosing the one path the whole field agreed to abandon.
  • The sibling bug is spec drift at the wire. Even native tool calling only standardizes the shape. An explicit null where the reference omits a field still slips through — the contract can't save you from a backend that speaks it loosely.

Why both survive to production

A demo exercises the happy path exactly once.

Both traps share a signature: a component that is structurally present and functionally empty, failing toward a value that looks legitimate. Empty history reads as forgetfulness. A dropped tool call reads as a model decision. Neither throws. Neither pages anyone. And a demo — one clean turn, one well-formed call — never lands on the input that reveals the hole. The gap between "wired" and "works" is exactly the set of inputs your demo didn't try.

Before you call it shipped

Four smoke tests that catch a hollow pillar

  • Turn 2 sees turn 1An integration test — not a mock — that runs two turns against the real store and asserts the second turn's history is non-empty. This single test would have caught Trap 01 on day one.
  • Log the parsed tool name, alarm on emptyEmit the resolved name for every call and alert when it's empty or unknown. A dropped or blanked call should page someone, not blend into "the model didn't call anything."
  • Diff the README against the codeFor each capability the docs claim works, point at the function that delivers it. Grep those layers for return [], return None, pass, TODO in bodies that are supposed to do work.
  • Test the wire, not the SDK's happy pathCapture real streamed chunks from your actual endpoint — explicit nulls, split arguments, wrapped blocks — and replay them through your parser. Provider conventions diverge exactly where your unit tests assume they won't.
